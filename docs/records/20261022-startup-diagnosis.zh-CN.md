# 启动与历史会话读取诊断（2026-10-22）

适用基线：Umi 0.2.1，提交 `5380271`，DB7。本次是故障定位，未修改运行代码、数据格式或发行包。前序局部复制优化见[旧会话性能记录](20261022-history-and-preview-performance.zh-CN.md)。

后续已按本诊断实施源码修复，见[启动与历史读取修复](20261022-startup-and-projection-cache.zh-CN.md)。下文保留诊断时点的基线与当时尚未实施的计划。

## 结论

历史首次打开的主要耗时是后台逐条重放原始事件。当前只有进程内状态缓存，重启后会重新计算；完整保留历史本身不要求每次显示都重算全部事件。另有两个独立问题：重放占住同一个后台执行线程，轻量请求也会排队；前端把尚未取得快照的会话显示为欢迎页，造成历史为空或没有响应的错觉。

启动也存在串行依赖：页面加载并挂载 React 后调用 `status`，才触发后台进程启动，后台就绪后再取列表和选中会话快照。本次后台就绪约0.62～0.84秒，其中模块导入约0.48～0.66秒。不能把这部分全部算成数据库启动慢。

没有证据证明 TypeScript 或 Node 的能力上限导致问题。同样的运行环境、相同完整会话，再次打开可以在几十毫秒显示。现有证据支持调整读取路径，无需改语言、删除原始记录或缩减模型能力。

## 证据与测量范围

用户提供的17.22秒录屏显示：界面框架先出现，历史稍后显示；切换已有会话时欢迎语重新出现，并持续数秒。按0.5秒抽帧定位现象，不把抽帧时间视为精确的操作计时。

检查了桌面快捷方式目标，安装目录版本为0.2.1；其 SQLite store 与 reducer 的构建文件哈希和当前源码构建一致。本次未从旧版运行记录推断新版表现。

真实数据库只读测量使用 `DatabaseSync({readOnly:true})` 和 `PRAGMA query_only=ON`，借用只读业务方法，不运行生产库的构造、迁移、恢复或写者锁。五条会话共388,126个事件；同日清点中385,120个是流式 `model.delta`。因此可见消息很少，不表示后台要重放的记录很少。

随后通过 SQLite backup 建立一致性隔离副本，确认没有待删除记录；副本启动未配置 API Key，使用离线验证模式。独立 Electron 窗口使用真实 renderer、preload、AgentBroker、agent-worker、DesktopService 和 SQLite 实现。诊断只允许列表、快照、事件及详情/附件读取命令。

“显示”计时为操作至快照返回、两个 animation frame 及用户消息 DOM 存在，是应用内绘制近似值，不是逐像素首帧证明。完整成功序列没有页面错误。诊断脚本早期因选择器错误、同名会话误选而中断，修正后才得到上述完整序列；这些失败不计为通过。早期关闭窗口时有未完成轮询随后台退出报错，后续脚本先卸载页面再关闭后台，未把它认定为产品运行故障。

不同轮次首次读取受系统文件缓存、CPU负载、JIT和测量位置影响，不能把上述单样本当p95。这里的“首次”指本进程未缓存该会话，并非清空Windows磁盘缓存。

## 代码定位

- `packages/adapters/src/sqlite/store.ts` 的 `projectionState()`：缓存未命中时，对选中会话所有事件执行SQL读取、JSON解析、Schema校验和归约。`snapshot()`最后复制完整状态。当前缓存仅为内存Map。
- `apps/desktop/service.ts` 的 `snapshot()`：取得状态后再组装用户消息、设置、上下文统计和资源事实。测量显示这些后续工作不是此次秒级延迟主体。
- `apps/desktop/agent-worker.ts` 与 `command-queue.ts`：查询和核心动作在同一后台运行环境处理。同步历史重放期间，其他请求无法及时处理；测量已证明轻量列表受影响，但未用真实活动模型测试停止延迟。
- `apps/desktop/main.ts`、`broker.ts` 与 renderer `App.tsx`：后台由页面的status请求触发，窗口加载、后台就绪、会话快照顺序等待。
- renderer `App.tsx`：切换时清空snapshot，`!snapshot?.messages.length`同时覆盖“加载中”和“真正为空”，因此显示错误的欢迎状态。

## 下一步最小改动及验收要求（尚未实施）

1. 增加可丢弃、可重建的持久化会话投影，保留所有原始事件。读取校验投影版本、会话/日志身份及事件位置，只归约后续事件；缓存损坏、版本不兼容或身份不符时退回完整重放。不能把缓存当成新的授权来源，也不能跳过未知副作用的启动恢复核验。
2. 避免在每个流式片段后保存整份快照；在合适的读取或稳定边界刷新派生数据。验收重启前后状态逐字段等价、追加事件、事务回滚、损坏缓存、恢复与权限事实，测写入开销，防止读取提速反而拖慢生成。
3. 明确区分启动中、历史加载中、加载失败与真正空会话。保留欢迎语、配色、侧栏宽度和正常输入能力；失败要有真实错误与重试入口。
4. 在测量基础上让后台初始化与窗口加载并行，保留原就绪错误。首次必须完整重建时，再评估分段调度或独立只读重建，避免引入第二Agent或庞大后台生态。

首要验收是重启后同一重会话显示时间明显下降，同时完整历史和恢复/授权结果不变。仅改加载文案、提高超时或提前在后台计算，不能宣称消除了重放成本。
