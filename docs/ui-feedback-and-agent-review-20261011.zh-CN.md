## 2. 文本截取：已复现的逻辑缺陷

`packages/agent/src/context/bounded.ts::toolResultViews` 每次投影都会截取所有保留的工具结果，包括刚执行的读取。

```text
budget = min(16384, max(512, floor(inputCeiling * 0.12)))
perResult = max(128, min(4096, floor(budget / 工具结果条数)))
超过 perResult 的结果只给首尾各 floor(perResult / 2) 字节
```

因此它不只处理旧长日志，也压缩模型当前正在读取的源码、历史和资料。结果条数增加会降低每条预算，哪怕其中其他结果很短。它没有优先保证本轮有效输入，也没有按真实结果长度分配预算。

隔离调用相同产品函数，inputCeiling=200000、每条2163字节：

| 工具历史条数 | 最新结果 |
| --- | --- |
| 1 / 4 | 完整 |
| 11 | 首0–744、尾1419–2163 |
| 30 | 首0–273、尾1890–2163 |

11条样本精确复现粘贴记录的744/744范围。它证明算法足以产生该现象；未访问生产数据库，不宣称真实运行一定恰好有11条保留结果。

另有放大因素：文件 `dataResult` 默认把 data JSON 放进 content，又保留相同 data；SQLite `settle` 再将整个 ToolResult 序列化成工具消息。源码正文被嵌套转义且重复。`read_history` / `read_artifact` 也采用类似 content+data，因此追回的内容可能再次受到相同投影裁剪。

这主要是上下文视图设计缺陷，不能归因于读取权限或模型“不够聪明”。记录中的模型为猜阈值花费大量思考，随后转 Shell；逐次批准和输出编码问题被一起放大。

还有一个证据契约缺口：完整 read_file 回执可以证明工具读过整个文件，却不证明模型实际看到了完整正文。整文件替换的已读保护需要明确这一差别。

建议契约（未实施）：

1. 持久 ToolResult / 原始消息不改写；另设唯一模型可见结果转换，正文只呈现一份，必要执行ID、hash、字节范围、结果状态保留。
2. 最新完整工具调用组优先保留工具已经承诺返回的范围。read_file、read_history、read_artifact、read_process_output 的按范围读取不能在下游再次无提示地截取。
3. 读取本身需要限额时，工具明确给出真实返回范围和 nextStartByte；范围内正文完整。UTF-8不能切断字符。
4. 总上下文接近真实预算时，沿现有完整消息组维护旧历史；超大新批次须明确范围/预算反馈，不能绕过模型输入上限。
5. 读取证据明确区分磁盘已观察范围和模型实际可见范围。整文件替换不应把隐藏中段当作模型已理解。

## 3. PowerShell：路径失败和乱码是两个问题

粘贴记录的第一次失败包含 `front/src/pages/front/src/pages/pages.css`：cwd 已在 pages 下，脚本又加了项目相对路径。第二次修正 cwd/相对路径后成功，修正的是寻址。

但输出仍含 `#< CLIXML`、首次模块准备进度及替换字符。`prepare.ts` 使用 `-EncodedCommand`，只设置 Console / OutputEncoding；`runner.ts` 将原生输出统一按UTF-8解码。这不保证 Windows PowerShell 所有错误/进度流的编码与表达格式一致。

建议窄修复：仅针对 Umi 自己的 PowerShell 启动包装，验证文本输出模式、关闭非必要进度、保证中文错误可读。保留完整原始输出资料；不要在前端简单删除 stderr，也不要为了修乱码更改所有用户脚本的 ErrorAction/退出语义。验收需包括中文 stdout、中文路径错误、非零退出、UTF-8分片及其他编码程序。本轮未修改此行为。

## 4. 停止延迟：已确认耦合，真实现场仍待复现

当前：

```text
App.stop → broker 等IPC回执（20s）
→ worker 串行队列 → service.handle(stop)
→ UmiApplication.stop 保存 run.stop_requested
→ AbortController.abort → await task.done
→ 工具退出 / 核验 / 结算 → run.stopped → 返回IPC
```

worker 的串行队列在等待 stop 完成期间也阻塞后面的 events / snapshot / 其他请求。用户可能已经请求停止，但界面无法及时看见 stopping。通用 COMMAND_TIMEOUT 文案又要求查询 commandId，而 stop 请求并不是用户输入 commandId，文案对象混淆。

另外，`CommandTools.reconcile(ctx)` 没有接收调用方的 AbortSignal；`runner.probe` 自身超时20s，恢复核验可能先探测桥接再探测子进程。ToolExecutor虽向reconcile传信号，此适配器实际未消费。停止不能及时打断这一段。执行器在某些同步准备 / SQLite / 文件操作期间也不能消费事件循环中的停止消息。

本轮证据：已有真实Node子进程树停止测试1/1通过；另用固定模型在专用临时数据中启动30秒PowerShell睡眠，在process.started后请求停止，核心stop耗时48.7ms，run=stopped、工具=cancelled，模型请求仍为1。该样本未经过Electron worker/broker，且未覆盖所有恢复路径，不能证明截图中等待三次超时的具体根因或桌面已修复。

建议契约（未实施）：

1. stop只在持久化停止意图并发出取消信号后返回accepted；清理完成通过原事件流通知。accepted不能冒充进程已退出。
2. 保持唯一写入者与执行循环；控制请求不应被等待完整任务收尾的IPC占住。不是把所有数据库命令任意并发化。
3. 文件、网络、执行和reconcile/probe的信号链明确贯通；停止后不再申请批准、派发新工具或请求新模型。
4. 已释放命令优先终止自有Job并保存回执；核验不能完成时保留unknown并停止新副作用。仅核对自有进程身份，不按名称或未验证PID杀进程。
5. 清理设有界等待，但超时不能写成“全部停止成功”。桌面可以显示停止已请求和仍未核验的操作。

## 5. 恢复按钮与自然续作

`inspectRecovery` 是读取预算、工具状态、未决执行和历史观察，既不执行reconcile，也不继续模型。因此用户看到的“检查恢复条件”不是实际恢复。

真正继续是 `resume → start(recovery=true) → claim → 原prepared/dispatched/unknown工具处理 → 模型循环`。核验未知副作用的依据是执行记录和回执；模型查阅历史用于理解任务，不能替代实际效果核验。

当前异常中断的run仍可占用environment.active_run_id。acceptInput将新消息加入它，但send只为queued/running/waiting_permission启动。隔离构造interrupted事实后发送“请继续”：消息已保存、同一个run、0次新模型请求、仍interrupted。自然输入续作确实没接通。

本轮经用户明确选择，移除“检查恢复条件”和第二阶段按钮，合并为一个“继续任务”。直接使用既有resume入口，后台仍做预算检查和原工具核验。未自动恢复、未改批准或未知执行规则。

后续建议：新输入进入异常中断会话时，应用先核验原执行，再把新输入和历史事实交给模型；明确stop后没有新输入则保持停止。拒绝是原操作的拒绝，不等于授权改写成另一条等价脚本。自然续作必须同时保证无重复执行、工具消息配对和输入commandId幂等。

## 7. Windows个人Agent的边界取舍（讨论方案）

建议把工作方式与宿主信任分开设置。选择工作区授权结构化文件访问，并不等于授权任意代码；同意宿主代码运行也不代表获得工作区文件/网络隔离。

| 能力 | 建议契约 | 实际限制 / 代价 |
| --- | --- | --- |
| 直接工作区文件 | 用户选择根；结构化工具默认在根内读写；保留真实已读版本检查、冲突反馈、编辑前备份/差异；额外文件通过用户选定扩展范围 | 对普通编码更直接，避免复制遗漏依赖；错误编辑立即影响项目。应用路径校验有竞争窗口，不能当OS隔离。副本模式可保留给需要审阅后交付的任务。 |
| 工作区外资料 | 默认由选定文件/目录授予只读范围；明确个人敏感资料的读取/发送策略；模型建议不自行扩大范围 | 会多一个范围确认，但不必每读几百字节批准一次。Shell获准后实际可读范围不能由这些工具规则保证。 |
| 网络工具 | 沿现有网络适配器补有界URL读取/下载，提供URL、状态码、内容类型、范围和失败原因；项目秘密不默认加入外部请求；凭据与模型配置由宿主提供 | URL、重定向、私网/回环目的地与认证要明确；受控网络工具只约束自身，不能限制获准Shell联网。 |
| 宿主命令 | 保留询问模式；另设明确的会话/工作区宿主执行信任，说明以当前Windows账户访问文件和网络；信任存用户配置、可撤销、绑定程序类别和有效期 | 原程序+完整argv批准精确但繁琐；项目构建脚本执行可改变行为。仅批准node/npm/PowerShell路径不能证明脚本安全，不能宣传“只在工作区执行”。 |
| 系统级操作 | 管理员提升、注册表、服务、计划任务、系统配置和破坏性外部操作单独确认；项目文件不得自行扩大宿主信任 | 此策略控制Umi工具派发，但任意获准代码仍可尝试同类动作；若需不可绕过保证，应使用可选隔离后端或专用受限账户环境。 |
| 停止与恢复 | 请求停止立即生效于后续派发，当前副作用真实核验；新输入续作沿唯一循环，unknown不重放 | Windows Job不控制外部服务等所有间接进程，无法承诺所有网络请求/外部副作用回滚。 |

不建议用命令词法“看起来只读”作为自动执行证明，也不建议把全目录hash恢复到执行前。哈希回答指定文件版本，权限回答允许调用什么，OS隔离回答代码实际能碰到什么，三者不能互相替代。

适合插件化的是FilePort工作方式、NetworkPort、ProcessPort实现与授权策略。继续使用现有registry/provider与唯一循环，不为此增加平行Agent或庞大插件平台。安装器、留存治理与OS沙箱不是普通任务的前置。
