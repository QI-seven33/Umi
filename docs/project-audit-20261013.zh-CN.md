# Umi 项目审查与整改路线（2026-10-13）

> 2026-10-13 后续更新：用户决定权限等待暂不开放自定义输入，改为独立问答工具。[阶段 A 实现与验收](stage-a-user-questions-and-review-20261013.zh-CN.md)优先于下文审查时的待办状态。

## 判断

当前架构值得保留，但日常使用尚未稳定。问题集中在执行限制没有充分识别真实进展、前端没有完整表达执行契约，以及多阶段补丁积累的维护成本。无需重写 Agent、换工作区模式或增加另一套任务平台。

这次暂停原生打开和桥编译缓存的后续开发，核对实际源码、已有 Git diff、入口引用、编译诊断、调用链和隔离 UI，并修复范围明确的问题。重大权限变化、数据迁移和大模块拆分只提出方案。修改前保存了 239 个非忽略文件；此前所有多阶段修改保留。

## 当前调用链与资源分配

桌面 renderer → 固定 preload → main/Broker → utility process 的命令队列 → DesktopService → UmiApplication → 唯一 AgentEngine。循环从原始消息和持久事实生成模型上下文，通过 DeepSeek 适配器请求；模型选择工具，ToolExecutor 准备对象、核对批准、执行适配器、保存结果，再交回模型。新消息入口与旧 resume 已分开，旧未决操作只核验，不因新消息自动重跑。

用户选择的目录记录为源目录；工作副本在 `dataRoot/environments/<environmentId>/working/<mountId>/`。资料区实际创建的是 `task/scratch`、`task/artifacts`、`task/research`、`task/logs`，并非旧建议中声称已经实现的通用 `task/cache`。桌面托管数据根来自 Umi 应用数据目录，用户选择的工作区目前不是这些缓存的存放根。ChangeSet 冻结副本变化后，经具体批准写回关联来源；独立成果可导出。任意自然语言交付位置与可选托管数据根仍需明确契约。

工作副本对内置文件工具有效；批准执行的宿主程序仍可接触副本之外的真实文件和网络。工作目录和 Windows Job 不能被描述成文件/网络隔离。

本轮重点代码：

## 仍需整改：UI 与产品逻辑

1. **审批挡住自然输入（P1）**：Composer 在 approvalPanel 存在时替换整块输入器。浏览器确认没有 textarea。用户无法在等待批准时直接说“换个任务”，虽然核心已经有新消息优先的处理。建议卡片保留具体允许/拒绝，旁边保留输入或“修改要求”入口；新消息取消旧准备/批准，再由模型判断。依照已接受的选择，等待批准期间不增加停止按钮。
2. **交付审阅不完整（P1）**：冻结预览只给 before/after 有界正文，侧栏不能继续查看冻结全文，也不是可靠的逐项差异查看。工作副本、冻结版本、原附件身份已区分，但仍缺少一致的变更列表、差异、删除项和二进制展示。长文件批准不能依赖预览中被隐藏的部分。
3. **刷新粒度过大（P1）**：FilePreview 用整个 environmentRevision 刷新当前工作文件，修改另一文件也会重置已加载页。改为目标文件的版本失效，保留当前分页与滚动位置；迟到请求仍不能覆盖新对象。
4. **成果和文件混用（P2）**：侧栏首页主要是 OutputsPanel，不是完整工作副本文件树；“+”实际是回到首页；任务检查点主要是过程工具结果。需要用户能看懂的“改了哪些文件、是否已交付、还缺哪步”，而非再添一个运行时调试面板。
5. **设置用语误导（P2）**：Docker/WSL 配置可保存、查程序可用性，并供模型选择具体宿主命令；未实现自动托管 provider、隔离或进程生命周期。“插件/启用插件”易被理解成自动接管执行。应改成可选执行环境说明或收起该占位；不是把这些现有配置误判成完全无用。
6. **归档交互与可访问性（P2）**：可恢复归档用了 1.2 秒长按；归档弹窗没有与设置相同的背景 inert 和完整焦点约束。建议普通确认并统一模态行为。重复“等待批准”的外层、活动组和卡片说明也可减负。

目前预览为文本/图片，不提供 HTML 页面视觉核验。脚本统计闭合标签只能确认局部结构，不能证明后半页无遮挡。Agent 也没有可靠的“打开已交付文件”工具；侧栏“工作副本位置”只是文件位置。用户要求“修复后打开”尚缺稳定的收尾动作。

## 与主流 Agent 的比较

没有一个必须照抄的“主流设计”。值得学的是可观察反馈、随时纠正、明确权限与贴近任务的工具。

- Claude Code 官方描述上下文收集、行动、验证随任务交替，用户可随时加入纠正，并有项目规则文件。Umi 的唯一循环方向一致；审批期间隐藏输入、默认硬轮次/重复限制和尚未建立项目规则加载契约是差距。见 [官方调用循环说明](https://code.claude.com/docs/en/how-claude-code-works)。
- Cursor 文档列出文件/搜索/终端及浏览器能力，并支持执行中加入消息。可借鉴反馈和视觉验收入口；闭源公开说明不能证明它的 Windows 隔离或持久化内部结构。见 [Agent 概览](https://cursor.com/docs/agent/overview)。
- OpenCode 将 allow/ask/deny、会话内再次允许和重复调用询问明确区分；其 doom_loop 是连续三次同工具同输入的询问策略。可参考提醒与用户纠正，不能直接变成 Umi 的任务失败契约，也不能把匹配规则说成 OS 隔离。见 [权限文档](https://opencode.ai/docs/permissions/)。
- 本地 Reasonix 选取源码快照固定在 studio `4041b48a8ead93876aac9122e4634fa1a412595a`，不是完整 checkout。Windows 文档明确没有 bash 文件沙箱；MultiEdit 与会话事实/缓存处理值得借鉴，其模糊匹配、编辑顺序及直接文件操作并不等于 Umi 的同原版本批量编辑与工作副本。见 [固定版本指南](https://github.com/esengine/DeepSeek-Reasonix/blob/4041b48a8ead93876aac9122e4634fa1a412595a/docs/GUIDE.zh-CN.md)。
- Harness 本地版本 `639ed015…` 与上阶段读取的官方 `d743267…` 需区分。沿单一循环、必要事实变化才追加的思想已采用；不复制其平台前提和截行方式。见 [官方仓库](https://github.com/deepseek-ai/deepseek-harness)。

工作副本与冻结交付符合 Umi 已确定的需求，不因其他产品更常直接编辑就改变。没有 Windows OS 沙箱也不意味着要把安装器、Docker 或留存治理设为每个任务的前置步骤。内置结构化文件/网络工具与宿主执行分别说明边界，才有可用的授权选择。

## 建议发展顺序与验收

| 阶段 | 小而具体的范围 | 验收，不以测试数代替完成率 |
| --- | --- | --- |
| A：问答、审阅和收尾 | 权限等待输入暂缓、保留扩展；独立问答选择/自定义回答；冻结全文与差异；目标版本刷新；交付后打开；明确可选执行设置 | 问答等待不继续模型请求，停止/新输入使旧问答失效，回答不成为批准；长文件完整可审阅；无关文件修改不重置预览；打开绑定真实交付版本 |
| B：速度与精度 | Windows 桥按固定源码/版本缓存；按工具角色识别进展；在 UI 给出任务级模型/工具/审批等待、请求量和实际 token，保持缓存稳定前缀 | 同输入读改测试与日常文件样本，分别记录成功率、反复读取、请求数、响应展示和停止时延；统计实际 API 返回与本地字节分开。可核验版本/可见范围与一次批量修改失败不写继续通过 |
| C：增量降耦合 | 从 DTO、会话同步、资源查询和文件预览开始拆窄接口；按组件合并 CSS；量化后再做无损存储优化 | 每次提取一个职责，旧记录/恢复/批准/流式结果一致；主题和窗口状态截图对照；原始历史及实际请求可完整重建 |

四类固定样本继续保留：①日常文件读改/交付/打开；②小项目读改测试；③跨文件并出现失败的编码任务；④停止、换目标、重启后未知原操作核验。先本地固定模型验证流程，真实模型质量需要明确的小规模付费验收；本轮不替用户调用。

任务内宿主信任值得设计，但应独立讨论授权范围、到期/撤销、程序类别、批准后的联网与外部副作用。任意宿主脚本获得执行权后，单靠路径描述无法强制它只在副本内操作。项目规则加载也需规定可信来源、作用路径与何时重新加载。它们不能靠前端一个 auto 开关落地。
