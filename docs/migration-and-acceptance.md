## 3. 数据和配置迁移规则

### 3.1 新数据库

新数据库使用独立位置、独立 schema 和版本记录。不得直接在旧数据库上新增列、重命名表或改写原始消息。开发期默认新会话验证，旧导入放在新核心已稳定后。

阶段 2 只建实际入口所需表，阶段 3 随资源和交付能力加入对应表，具体清单见 C11。禁止为了“未来可扩展”预建大量未使用表。

消息、事件、工具执行和批准事实要保持可追溯关联。旧缺失结果不补造成功；导入明确标记 `import` 来源、不触发执行、不恢复旧的临时宽泛批准。无法确认的工具保持 unknown（结果未知），提供核验入口。

### 3.2 旧会话与环境

未来导入采用离线方式：旧服务停止写入 → 读取一致快照 → 校验消息及副本清单 → 建立新 ID 映射 → 写入新数据库 → 验证历史投影与文件内容 → 用户切换。

副本中尚未交付的文件不能遗漏；保留旧环境与旧源目录的映射及指纹。导入期间不写回源目录、不继续原副作用。旧事件序号不能直接成为新会话的 cursor。

旧数据库损坏、缺失事件或原路径已变化时，返回具体迁移问题；不能通过摘要“补齐”不存在的执行事实。

### 3.3 配置与秘密

模型、思考、权限及语言属于会话配置；头像、用户名和视觉偏好属于个人配置。它们按已有用户设置迁移，不以新默认覆盖已有选择。

API Key 不写进设计文件、Git、事件、请求快照或导入报告。模型路由保留实际接口含义；搜索传输独立配置。桌面安全存储具体实现放在阶段 5，阶段 2 通过明确环境配置读取，不复制旧 `.env` 到新项目。

请求快照保留可重现的请求正文、工具规格及版本，但认证信息排除。读取快照和附件的权限也需要约束，它们可能包含用户内容。

## 4. 分阶段实施

### 阶段 1：设计基线（本次）

交付本文件、架构、契约和 README。固定 ADR01—ADR10，确认一个循环、一个上下文入口、一个归约及唯一事实来源。

完成标准：文档之间的身份、状态、授权、压缩和恢复规则一致；旧代码对照可定位；下一阶段可以直接按契约实现。

### 阶段 2：无界面核心和上下文基础

实施顺序：

1. 建立最小 TS 工作区、严格类型检查和运行时校验；固定 Node、TS、SQLite 驱动及模型客户端版本。
2. 建立共享事件协议、纯归约和独立 SQLite 写入入口；把输入命令、运行身份和幂等接收跑通。
3. 建立 Context Manager 唯一准备入口，保留完整用户事实、模型配置、消息组和来源；冻结每次实际请求；接同会话 search_history/read_history，验证旧原文找回及要求更正。
4. 用确定性模型模拟器验证文本、思考、工具 block、完整参数、等待批准和结果回填；模拟器替换适配器，不建立第二个 Agent。
5. 接 DeepSeek 专用适配器，验证原始 reasoning 回传、真实模型能力、工具协议和 usage。保留搜索适配入口，实际搜索沿用现有可用语义。
6. 接入最小批准工具和恢复入口，验证停止、断线、重放、配额耗尽、重试边界；先不执行任意宿主命令。

第一个纵向闭环：原始用户输入 → 持久接收 → 准备并冻结请求 → 流式 block → 具体工具请求 → 批准阻塞 → 工具结果 → 下一模型轮 → 最终回答 → 重启后同一投影。

阶段 2 的 Environment 先建立稳定身份、持久位置绑定与独占规则；真实资源物化和交付在阶段 3A 接入。最小批准工具只在该环境的 task/scratch 区产生可核验效果，不能拿模拟结果宣称真实文件交付完成。“临时”表示文件用途，不表示任务重启时可以丢失其位置和未核验效果资料。执行记录引用 environmentId、派发时修订及执行定位快照，不能将目录路径作为环境 ID。

阶段 3A 在环境中增加 working 区与资源挂载，不替换旧 scratch 根或改写历史执行记录。独立验收环境无需变成用户的正式项目环境；共享的是数据契约。临时资料只有在无活动执行/待核验效果、满足资料保留规则后才可清理。

当前实现固定 Node `v24.11.0`、npm `11.6.1`、TypeScript `7.0.2`、Zod `4.6.5`、Node 类型 `24.10.0`。采用单个 node:sqlite 适配器，已验证事务、唯一写入者与进程硬退出；该 API 在本运行环境仍有实验性警告。桌面运行环境另行验收。

出口门槛：A01—A20、A34 的阶段 2 部分、A42、A44 的核心部分及 A45 的阶段 2 部分通过；真实 DeepSeek 请求完成至少一个带工具的多轮闭环。真实 API 验证记录模型 ID、日期、适配器版本和脱敏 usage，不使用旧截图代替。tool_executions、approval_requests、artifacts 按 C11 自阶段 2 建立，不等待资源或命令阶段。

### 阶段 3A：受控文件、资源和交付

实施顺序：

1. 绑定初始工作区；建立托管环境目录和文件清单，延续同会话环境。
2. 发现外部候选资源，只返回允许的元数据及扫描范围；固定目标后申请具体资源权限。
3. 物化真实文件到工作副本，建立资源映射、基线和可读取来源。
4. 接入读、写、列举、文本搜索和文件预览的结构化工具；所有源目录写入经过交付契约。
5. 构建不可变 ChangeSet，批准后逐项写回、核验和记录回执；处理冲突、部分失败和崩溃窗口。
6. 接入真实原生回收站；不支持的平台或运行环境返回能力缺失。

出口门槛：A21—A28、A36、A45 的阶段 3A 部分通过；源文件未获相应批准时不发生写回；未交付副本在新 run 中仍可访问；交付等待不会继续触发后续模型调用。

### 阶段 3B：宿主命令与进程

先实现 program + argv（固定程序与参数）的结构化请求，再开放 Shell 脚本。直接命令、项目测试、构建、Git 和 Shell 共用权限及派发入口。

启动前固定 cwd、程序、参数、脚本内容摘要、environmentRevision、环境变量范围、超时及输出上限，提交派发意图后再启动。输出归档、进程身份、取消清理和未知结果核验一起实施；批准后依赖文件改变也触发批准失效。

`cwd`（工作目录）不等于沙箱。宿主环境不声称限制任意脚本的全部文件或网络访问；项目脚本、Git hooks（钩子脚本）等间接代码执行也按宿主能力处理。Docker/WSL 插件按真实隔离能力报告，互不绑定。

出口门槛：A29—A32、A43 的 Windows 宿主场景通过；批准失效时进程未释放；停止能核对普通进程树清理结果；无法确认的外部效果阻塞自动续跑。A33 的默认宿主工作不依赖 Docker/WSL 已满足，插件配置和失败路径延至阶段 5；不为尚未使用的插件创建空壳或独立调度系统。没有 OS 文件/网络隔离，外部服务代启动进程不纳入普通进程树保证。

### 阶段 4：长任务上下文和记忆

阶段 2 的上下文入口继续扩展，不另建一套记忆引擎。

加入有来源的要求清单、任务笔记、历史查找、资料范围读取、完整消息组压缩及上下文版本切换。模型可见的是经过预算的会话事实、实际状态与资料引用；界面折叠状态、调试日志和全部原始事件不直接入模。

Token 估算、实际 usage、剩余预算、压缩覆盖范围和缓存命中分别展示；未知数据不显示为零。模型输出预算和压缩阈值使用真实任务样本调整，不把 1M 全用满作为验收目标。

出口门槛：A34—A35、A37 通过；长任务包含修改要求、否决方案、断线与外部变化时，能够回到原文；压缩不篡改原消息、不破坏保留消息的 DeepSeek 协议；固定状态不被模型笔记覆盖。

### 阶段 5：现有前端与桌面对接

先用传输适配层对接现有 React UI，再接 Electron 主进程、preload（受限预加载桥）和 utility process（独立 Agent 子进程）。保留当前视觉风格和用户近期修改。

### 5.1 验证方式

持久化故障用确定性注入点验证：事务前、提交后、发布前、派发前、效果后、结果提交前。注入不会成为产品入口。

独立进程重启测试必须实际退出进程并重新读取数据库，不以清空几个内存对象代替。文件和回收站测试只使用专用测试资源；不处理旧用户桌面文件或真实未交付项目作为验收材料。

归约验证使用同一事实记录的不同分片、重复和重放次序；合法排序后的投影一致。字段校验测试须涵盖损坏旧记录、异常模型返回和插件结果，不能只检查 TS 编译。

上下文验收使用固定任务样本，逐条检查关键要求、原文引用和否决原因可取回；评价模型是否依要求行动时登记模型 ID 与真实响应。模拟器只能证明循环和协议状态，不能证明模型质量、语言遵从率或缓存成本。

真实 API 探测涵盖文本、思考、带工具连续回传和所需附件能力。模型宣称支持图片不等于当前传输路径已支持；无法接收时返回明确能力说明。对用户展示中文通过提示词与语言设置引导；原始响应不改写成伪造的“原始思考”。

原生 Windows 文件身份、进程树清理和回收站选择具体实现后，用真实平台验收。相同接口在无能力的平台上明确失败，不能以模拟成功替代。
